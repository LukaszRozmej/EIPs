## Abstract

Under [EIP-8037](./eip-8037.md), every call frame can use the whole `state_gas_reservoir` of the transaction, whatever gas its caller forwards. A callee can therefore make the sender pay for much more state than its gas budget suggests, and can empty the reservoir that later frames of the same transaction rely on. This proposal gives each call frame below the top level a ceiling on the net state-gas of the transaction. The ceiling allows the frame to create as many new state bytes as its forwarded gas could buy before [EIP-8037](./eip-8037.md). A frame that exceeds it halts as on out-of-gas, and its caller continues.

## Motivation

[EIP-8037](./eip-8037.md) passes the reservoir to every child frame in full. The 63/64 rule of [EIP-150](./eip-150.md) and the gas argument of a call limit only `gas_left`. For a new slot, a new account and `CREATE`, the legacy share of [EIP-8037](./eip-8037.md) limits the state-gas that a frame can take from the reservoir to a few times its gas. The code deposit has no such limit: a callee with about 50,000 gas can deploy about 1 KiB of code and take about 1.75M state-gas from the reservoir. This has two effects:

1. **Cost to the sender.** The sender pays for state that untrusted code creates, up to the whole reservoir. Bundlers, relayers and keepers that execute untrusted code with a fixed budget cannot bound this cost by the budget.
2. **Interference between calls.** A callee that empties the reservoir changes the cost of later state creation in the same transaction. A later frame then pays the full state-gas from its own `gas_left`, and a fixed budget that was sufficient with the reservoir can run out of gas. For example, a batch of callbacks, each with a fixed budget, can fail after an earlier callback empties the reservoir.

Before [EIP-8037](./eip-8037.md), the gas that a caller forwards limited everything that a callee could cost, including state: the cheapest new state byte cost 200 gas, as code deposit. This proposal restores that limit for state-gas, with the only input that deployed contracts give: the forwarded gas.

## Specification

### Parameters

| Parameter | Value |
|---|---|
| `LEGACY_GAS_PER_STATE_BYTE` | 200 |

`LEGACY_GAS_PER_STATE_BYTE` is `GAS_CODE_DEPOSIT` before [EIP-8037](./eip-8037.md), the lowest gas per new state byte of any operation before [EIP-8037](./eip-8037.md).

### State-gas ceiling of call frames

Each call frame has a `state_gas_ceiling`, the highest value of `evm_state_gas_used` that the frame and its descendants can reach.

- The top-level frame has no ceiling.
- A frame that a `CALL`, `CALLCODE`, `DELEGATECALL`, `STATICCALL`, `CREATE` or `CREATE2` starts with `child_gas` of `gas_left` (after the 63/64 rule and including the call stipend) gets:

  ```python
  child.state_gas_ceiling = min(
      parent.state_gas_ceiling,  # no limit if the parent has none
      evm_state_gas_used + child_gas * CPSB // LEGACY_GAS_PER_STATE_BYTE)
  ```

- After each state-gas charge of [EIP-8037](./eip-8037.md), the frame that is charged checks `evm_state_gas_used > state_gas_ceiling`. If that is true, the frame halts exceptionally, as on out-of-gas. Its state changes and its state-gas are rolled back as [EIP-8037](./eip-8037.md) specifies for an exceptional halt, and its `gas_left` is consumed. The caller continues, and can detect the failure as for any failed call.
- The account-creation charge of a `CALL*` with value and of a `CREATE`/`CREATE2` is charged to the calling frame, before the child frame starts. The code-deposit charge is charged to the create frame when its init code returns, and is checked against the ceiling of the create frame. If the check fails, the code deposit fails, as when the create frame cannot pay the code-deposit cost.
- A refill lowers `evm_state_gas_used`, so it frees room under the ceiling for later charges. A rollback restores `evm_state_gas_used` to its value at the snapshot of the frame, which already passed the checks, so a rollback cannot take it above a live ceiling. The rollback runs no check.

`child_gas * CPSB // LEGACY_GAS_PER_STATE_BYTE` is the allowance derived from the forwarded gas: the net state-gas that the frame can create. The actual allowance, `state_gas_ceiling` minus `evm_state_gas_used` at the frame's entry, is smaller when the parent has less of its own allowance left.

The ceiling applies to all state-gas, whichever pool pays it. State-gas that a frame pays from its own `gas_left` costs one gas per unit, so it can never exceed the ceiling on its own: in practice, the ceiling limits what a frame takes from the reservoir.

## Rationale

### The allowance follows the forwarded gas

Deployed contracts limit what a callee can cost only through the gas argument of a call. Before [EIP-8037](./eip-8037.md), a frame with `g` gas could create at most `g / LEGACY_GAS_PER_STATE_BYTE` new state bytes: code deposit cost 200 gas per byte, a new account about 208 gas per byte, `CREATE` about 267, and a new slot about 312. The allowance gives exactly that number of bytes, at the price of [EIP-8037](./eip-8037.md): about `7.65 × g` of state-gas (`CPSB / 200`). Thus:

- The allowance never fails a call whose execution creates no more new state bytes than its gas could buy before [EIP-8037](./eip-8037.md). On the same execution path, a gas budget that was sufficient for state creation stays sufficient.
- A callee can take at most about `7.65 × g` from the reservoir. A sender that executes untrusted code with fixed budgets can fund every callee in full: it supplies a reservoir of `CPSB / LEGACY_GAS_PER_STATE_BYTE` times the gas it forwards to untrusted code, plus its own state-gas. Then no callee can empty the reservoir for a later one.
- The allowance depends only on the forwarded gas, not on `tx.gas`, so a sender cannot use it to make a call fail that would succeed otherwise, beyond what the forwarded gas already allows.

### A ceiling, not a pool

The ceiling is an absolute value of `evm_state_gas_used`. A child's ceiling is never above its parent's, so the net state-gas of a frame and all its descendants stays within the frame's allowance. Because the parent does not run while the child runs, only the frame that is charged must be checked. The ceiling moves no gas between pools and changes no accounting of [EIP-8037](./eip-8037.md): each frame keeps one value, and each state-gas charge makes one comparison.

### The top level has no ceiling

The sender controls the top-level frame, so the sender's own state creation is limited only by `tx.gas`, as in [EIP-8037](./eip-8037.md). A deployment from the transaction itself, or from a factory that the transaction calls directly, keeps the large deployments that [EIP-8037](./eip-8037.md) allows.

### Exceeding the allowance halts the frame

A frame that exceeds its allowance halts as on out-of-gas, so the failure stays local, as callee failures always were. The transaction does not fail, and the caller can handle it like any failed call.

### A lower ratio

A lower ratio, for example from the 312 gas per byte of a new slot before [EIP-8037](./eip-8037.md), would expose senders less. But it would fail deployments from call frames that the same gas could complete before [EIP-8037](./eip-8037.md).

## Backwards Compatibility

This proposal changes the result of transactions and requires a scheduled network upgrade.

- A call frame that creates more state than its forwarded gas could buy before [EIP-8037](./eip-8037.md) halts as on out-of-gas. Under [EIP-8037](./eip-8037.md) without this proposal, such a frame could use the reservoir.
- A deployment from a call frame needs at least 200 gas of forwarded gas per byte of code, unless the same frame refills state that offsets it (the allowance limits net new state, not the bytes deployed). For example, a 24 kB deployment from a call frame needs at least 4.9M forwarded gas, while its execution under [EIP-8038](./eip-8038.md) costs about 100,000. Before [EIP-8037](./eip-8037.md), the same deployment needed the same 4.9M of gas. A frame with 16.7M gas can deploy about 83 kB, which is sufficient for one contract of the maximum size of [EIP-7954](./eip-7954.md).
- A contract that deploys code in a loop until `gasleft()` is low, inside a call frame, runs more iterations than before [EIP-8037](./eip-8037.md), because the code deposit takes less execution-gas, and can exceed its allowance. Before, the same loop stopped earlier and succeeded.

## Test Cases

- A transaction with `tx.gas` above `TX_MAX_GAS_LIMIT` forwards 50,000 gas to code that runs `CREATE` with the init code `0x6160005ff3`, which returns 24,576 zero bytes. The account-creation charge (183,600) fits the allowance of 382,500. The code deposit (37,601,280) exceeds the ceiling of the create frame. Only the `CREATE` fails; the reservoir keeps the code-deposit state-gas, and the transaction continues.
- A frame whose net state-gas is exactly at its ceiling succeeds; one unit above, it halts.
- A child is limited by the remaining allowance of its parent.
- A refill in a frame frees room for a later charge of the same frame.
- A batch that calls three untrusted callees with explicit budgets: one callee deploys a large contract; it fails alone, and the other two create their state from the reservoir.

## Security Considerations

The allowance limits what untrusted code can take from the reservoir, but it does not reserve that amount. A sender that supplies a smaller reservoir than the sum of the allowances of its untrusted calls can still find the reservoir empty for a later call. That call then pays state-gas from its own `gas_left`, as under [EIP-8037](./eip-8037.md).

Contracts that bill sub-calls by `gasleft()` differences cannot see the state-gas that a callee takes from the reservoir. The allowance bounds it at about 7.65 times the forwarded gas.
