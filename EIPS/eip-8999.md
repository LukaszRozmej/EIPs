## Abstract

This proposal replaces the reservoir model of [EIP-8037](./eip-8037.md) with a single settlement at the end of the transaction. State-creating operations do not take state-gas from `gas_left`. They only increase a counter of the transaction's net state-gas, which is part of the state that a frame's rollback undoes. When execution ends, the counter is paid from the gas that execution did not use. If that gas is not sufficient, the transaction fails as a whole. A call frame can create net state-gas only up to an allowance derived from the gas forwarded to it, so a caller still limits what a callee can cost. A new `STATEGAS` opcode returns the net state-gas used so far. The pricing (`CPSB`), the two-dimensional block accounting and the [EIP-7825](./eip-7825.md) cap on execution gas of [EIP-8037](./eip-8037.md) do not change. The execution-gas charge of each state-creating operation is not lower than its cost before [EIP-8037](./eip-8037.md). An optional extension settles the execution-gas increases of [EIP-8038](./eip-8038.md) in the same way, so that call frames keep the costs from before [EIP-8038](./eip-8038.md).

## Motivation

[EIP-8037](./eip-8037.md) meters state-gas separately from execution-gas, so that the [EIP-7825](./eip-7825.md) cap applies to execution only and large contracts can still be deployed. Because a transaction has a single gas limit, it splits `tx.gas` into `gas_left` and a `state_gas_reservoir`. State-gas is taken from the reservoir first and from `gas_left` after that, and refills and rollbacks return state-gas to `gas_left`.

This puts state-gas inside the call frames, and makes the gas that a frame can see and use depend on things the frame does not control:

1. **Spent gas comes back.** Clearing a slot that was zero at the start of the transaction returns state-gas to `gas_left` at once. A frame that reverts returns to its caller the state-gas it paid from `gas_left`. Contracts that inspect `gasleft()` after a failed call to tell an out-of-gas failure from a logic error can then draw the wrong conclusion.
2. **The sender sets the in-frame price of state creation.** With a reservoir (`tx.gas > TX_MAX_GAS_LIMIT`), a frame pays only the execution part of a new slot (12,100 gas when cold, compared with 22,100 before). A failure handler that used to run out of gas can complete. Without a reservoir, the frame pays the full 110,020 gas, and a sub-call budget that was sufficient before can run out of gas. Both directions are available to an attacker who sends the transaction.
3. **The accounting is complex.** The reservoir model needs four counters, three of them frame-local, a last-in, first-out refill order, a merge step for successful children, a separate restore rule for rollbacks, and a commit rule for [EIP-7702](./eip-7702.md) authorizations.

All three come from charging state-gas inside frames. The amount of state a transaction creates is known only at the end, and it is a property of the transaction, not of a frame. This proposal settles it once, at the end.

## Specification

The parameters and the state-gas amounts of [EIP-8037](./eip-8037.md) apply: `CPSB`, `STATE_BYTES_PER_STORAGE_SET`, `STATE_BYTES_PER_NEW_ACCOUNT`, `STATE_BYTES_PER_AUTH_BASE` and `TX_MAX_TOTAL_GAS_LIMIT`, and the operations listed in its sections "Gas accounting for SSTORE (opcode-level)" and "Gas accounting for new accounts". The transaction validity rules and the block-level accounting of [EIP-8037](./eip-8037.md) apply as specified there, with `tx_output.evm_state_gas_used` replaced by `tx_state_gas` below.

This proposal replaces the section "Transaction-level gas accounting (reservoir model)" of [EIP-8037](./eip-8037.md), including its subsections on halts, reverts and successful children. `state_gas_reservoir`, `state_gas_from_gas_left`, `state_gas_baseline` and `state_gas_committed` are removed.

### Parameters

| Parameter | Value |
|---|---|
| `LEGACY_GAS_PER_STATE_BYTE` | 200 |
| `STATEGAS` opcode | `0x4c` (provisional) |
| `STATEGAS` gas cost | 2 |

`LEGACY_GAS_PER_STATE_BYTE` is `GAS_CODE_DEPOSIT` before [EIP-8037](./eip-8037.md), the lowest gas per new state byte of any operation before [EIP-8037](./eip-8037.md).

### Pre-execution

During the pre-execution phase of [EIP-2780](./eip-2780.md):

```python
evm_gas = tx.gas - intrinsic_gas
execution_budget = TX_MAX_GAS_LIMIT - intrinsic_gas
pre_execution_gas = 0     # runtime execution-gas of EIP-2780
committed_state_gas = 0
for authorization in tx.authorization_list:  # in order, as in EIP-7702
    pre_execution_gas += <runtime execution-gas of the authorization>
    committed_state_gas += <state-gas of the authorization>
    if (pre_execution_gas > execution_budget
            or pre_execution_gas + committed_state_gas > evm_gas):
        pre_execution_failure()
gas_left = min(execution_budget - pre_execution_gas, evm_gas - pre_execution_gas - committed_state_gas)
gas_left_initial = gas_left
state_gas_limit = evm_gas - pre_execution_gas - committed_state_gas
state_gas_used = 0
```

`committed_state_gas` is the state-gas of the pre-execution charges that a rollback of the top-level frame does not undo, which are the [EIP-7702](./eip-7702.md) authorization charges. It is paid before execution starts. The authorizations are charged one at a time, so a later authorization can fail after earlier ones were charged. Each of these counters only grows during pre-execution: no step resets execution-gas that pre-execution already used.

The charges of one valid authorization are those of [EIP-2780](./eip-2780.md) and [EIP-8037](./eip-8037.md), in this order:

1. State-gas `STATE_BYTES_PER_NEW_ACCOUNT × CPSB`, if the authority does not exist.
2. Execution-gas `ACCOUNT_WRITE`, when [EIP-2780](./eip-2780.md) requires it: not if the authority is the transaction sender (its write is paid by `TX_BASE_COST`), not if it is the recipient of a transaction with value (paid by `TX_VALUE_COST`), and not if an earlier authorization of the same transaction already wrote it.
3. State-gas `STATE_BYTES_PER_AUTH_BASE × CPSB`, if the authorization sets a delegation on an authority that had no delegation at the start of the transaction and that no earlier authorization of the transaction delegated.

The execution part of `PER_AUTH_BASE_COST` stays in intrinsic gas, as in [EIP-2780](./eip-2780.md). The authority is accessed before its first charge, so a failed authorization leaves its authority in the block access list.

A pre-execution failure is processed as an out-of-gas in the pre-execution phase of [EIP-2780](./eip-2780.md): all authorizations are rolled back, and the execution-gas is consumed. The accesses that pre-execution made before the failure stay in the [EIP-7928](./eip-7928.md) block access list, as in [EIP-2780](./eip-2780.md). The settlement does not run, and:

```python
tx_gas_paid = max(intrinsic_gas + min(evm_gas, execution_budget), calldata_floor_gas_cost)
tx_state_gas = 0
tx_execution_gas = tx_gas_paid
```

For example, with 110,000 gas after intrinsic gas, three authorities that exist and have no delegation need 3 × 9,000 execution-gas and 3 × 35,190 state-gas. Each charge fits alone, but after the third authorization `27,000 + 105,570 > 110,000`, so pre-execution fails, all three authorizations are rolled back, and the sender pays all of `tx.gas`.

The account-creation charge of a contract-creation transaction is undone by a rollback of the top-level frame. It is added to `state_gas_used` when the top-level frame starts, before any init code runs, and the check against `state_gas_limit` below applies to it. Thus a contract-creation transaction to a non-existent address needs `tx.gas - intrinsic_gas - pre_execution_gas - committed_state_gas >= STATE_BYTES_PER_NEW_ACCOUNT × CPSB`, or it fails with a settlement failure before its init code runs. The same applies to the account-creation charge of a transaction that transfers value to a non-existent account.

### State-gas during execution

`state_gas_used` is part of the state of the transaction. It is not part of `gas_left`:

- A state-gas charge listed in [EIP-8037](./eip-8037.md) adds its amount to `state_gas_used`. It does not change `gas_left`.
- A state-gas refill listed in [EIP-8037](./eip-8037.md) subtracts its amount from `state_gas_used`. It does not change `gas_left`.
- When a frame reverts or halts exceptionally, `state_gas_used` is set back to its value at the entry of the frame, together with the other state changes of the frame. The remaining `gas_left` of the frame is returned to the parent or consumed, as before [EIP-8037](./eip-8037.md).
- After each state-gas charge, the allowance check of the charged frame is applied first (see [State-gas allowance of call frames](#state-gas-allowance-of-call-frames)). If the charge passes it and `state_gas_used` is then greater than `state_gas_limit`, the transaction fails at once with a settlement failure. Execution stops: no further instruction is executed in any frame.
- The account-creation charge of a `CALL*` that transfers value to a non-existent account is added when the transfer is made. If the target has no code and is not an active precompile, nothing in the call can undo the transfer, so an implementation can apply the charge without a child frame. A precompile has no code but can fail, for example on invalid input or out of gas, and then its transfer and the account-creation charge are undone. In all cases, the charge is undone when a frame that contains the `CALL*` rolls back.

The `GAS` opcode returns `gas_left`. The 63/64 rule of [EIP-150](./eip-150.md) and the `SSTORE` stipend check of [EIP-2200](./eip-2200.md) apply to `gas_left`, as before [EIP-8037](./eip-8037.md).

### State-gas allowance of call frames

Each call frame has a `state_gas_ceiling`, the highest value of `state_gas_used` that the frame and its descendants can reach.

- The top-level frame has no ceiling. Only `state_gas_limit` applies to it.
- A frame that a `CALL*`, `CREATE` or `CREATE2` starts with `child_gas` of `gas_left` (after the 63/64 rule and including the call stipend) gets:

  ```python
  child.state_gas_ceiling = min(
      parent.state_gas_ceiling,  # no limit if the parent has none
      state_gas_used + child_gas * CPSB // LEGACY_GAS_PER_STATE_BYTE)
  ```

  `child_gas * CPSB // LEGACY_GAS_PER_STATE_BYTE` is the allowance derived from the forwarded gas: the net state-gas that the frame can create. The actual allowance, `state_gas_ceiling` minus `state_gas_used` at the frame's entry, is smaller when the parent has less of its own allowance left.

- After each state-gas charge, including the code-deposit charge of a create frame, the frame that is charged checks `state_gas_used > state_gas_ceiling`. If that is true, the frame halts exceptionally, as on out-of-gas: its state changes are rolled back, which also removes the charge, and its `gas_left` is consumed. The caller continues, and can detect the failure as for any failed call. A refill lowers `state_gas_used`, so it frees allowance for later charges of the same frame.
- The account-creation charge of a `CALL*` with value and of a `CREATE`/`CREATE2` is charged to the calling frame, before the child frame starts. The code-deposit charge is charged to the create frame when its init code returns: it is checked against the ceiling of the create frame at that point. If the check fails, the code deposit fails, as when the create frame cannot pay the code-deposit cost.

The allowance check is applied before the check against `state_gas_limit`. A charge that exceeds the ceiling of the charged frame fails only that frame, also when it would exceed `state_gas_limit` too. Only a charge that is within the ceiling, or a charge to the top-level frame, is checked against `state_gas_limit`. Thus untrusted code in a call frame cannot make the transaction fail through a single charge that exceeds both limits, for example a large code deposit.

### `STATEGAS` opcode

`STATEGAS` takes no input. It pushes `state_gas_used`, the net state-gas of the transaction so far, without `committed_state_gas`. It costs 2 gas. The value can decrease, because refills and rollbacks decrease `state_gas_used`, so the difference between two `STATEGAS` reads can be negative. In a contract-creation transaction, the value includes the account-creation charge of the transaction from the first instruction of the init code.

### Execution-gas of state-creating operations

A state-creating operation takes from `gas_left` exactly its total charge before [EIP-8037](./eip-8037.md) and [EIP-8038](./eip-8038.md), for the same case, instead of its execution-gas charge under [EIP-8038](./eip-8038.md):

| Operation | Charge to `gas_left` (warm / cold) |
|---|---|
| `SSTORE` that creates a slot (original and current value zero, new value non-zero) | 20,000 / 22,100 |
| `CALL` with value to a non-existent account | 34,100 / 36,600, plus memory expansion |
| `SELFDESTRUCT` whose balance transfer creates an account | 30,000 / 32,600 |
| `CREATE`, `CREATE2` (account part, whether or not the address exists) | 32,000, plus the init-code costs as before |

In each case, the charge is higher than the execution-gas charge of [EIP-8038](./eip-8038.md) for the same case, so no part of it, such as the access cost or `CALL_VALUE`, is charged again. These charges are execution-gas. The code-deposit charge and the pre-execution charges are not changed.

"Warm" and "cold" refer to the slot or account before the instruction.

Whether a `CALL` or `SELFDESTRUCT` creates an account is known only after the target is accessed. These instructions are charged in two parts, so that the charge before the access does not depend on the target:

1. Before the access, under the rules of [EIP-7928](./eip-7928.md), the instruction takes its execution-gas charge of [EIP-8038](./eip-8038.md) for the case without an account creation, for example `COLD_ACCOUNT_ACCESS + CALL_VALUE` for a cold `CALL` with value.
2. After the access, if the instruction creates an account, it takes the difference up to the total in the table. If `gas_left` cannot pay this difference, the frame halts exceptionally as on out-of-gas, and the target is in the block access list.

An `SSTORE` that creates a slot is charged after the slot is read, as under [EIP-8038](./eip-8038.md).

An `SSTORE` that restores a slot to an original value of zero (original value zero, current value non-zero, new value zero) adds 19,900 (`GAS_STORAGE_SET - WARM_ACCESS`, as before [EIP-8037](./eip-8037.md)) to the refund counter, instead of the `STORAGE_WRITE` of [EIP-8038](./eip-8038.md). The refund cap applies.

### Settlement

When the top-level frame ends, the transaction computes three quantities: `tx_gas_paid`, the gas the sender pays; `tx_execution_gas` and `tx_state_gas`, its contribution to the two block dimensions. `surcharge_used` is zero unless the [repricing surcharge](#repricing-surcharge-extension) applies.

```python
exec_gas_used = gas_left_initial - gas_left
settlement_gas = state_gas_used + surcharge_used
if settlement_gas > state_gas_limit - exec_gas_used:
    # settlement failure
    paid = min(tx.gas, intrinsic_gas + pre_execution_gas + committed_state_gas + gas_left_initial + surcharge_used)
    tx_gas_paid = max(paid, calldata_floor_gas_cost)
    tx_state_gas = committed_state_gas
    tx_execution_gas = max(intrinsic_gas + pre_execution_gas + gas_left_initial + surcharge_used, calldata_floor_gas_cost)
else:
    tx_state_gas = committed_state_gas + state_gas_used
    tx_gas_used_before_refund = intrinsic_gas + pre_execution_gas + exec_gas_used + surcharge_used + tx_state_gas
    tx_gas_refund = min(tx_gas_used_before_refund // 5, refund_counter)
    tx_gas_used_after_refund = tx_gas_used_before_refund - tx_gas_refund
    tx_gas_paid = max(tx_gas_used_after_refund, calldata_floor_gas_cost)
    # EIP-7778: refunds lower the payment, not the block gas
    tx_execution_gas = max(tx_gas_used_before_refund - tx_state_gas, calldata_floor_gas_cost)
```

Without [EIP-7778](./eip-7778.md), `tx_execution_gas` uses `tx_gas_used_after_refund` instead of `tx_gas_used_before_refund`, as in [EIP-8037](./eip-8037.md).

- The sender pays `tx_gas_paid` at the effective gas price and gets back `tx.gas - tx_gas_paid`. `tx_gas_paid` is never greater than `tx.gas`.
- `tx_gas_paid` is burned at the base fee, and the proposer gets `tx_gas_paid` at the priority fee.
- The receipt `cumulative_gas_used` adds `tx_gas_paid`.
- `tx_execution_gas` and `tx_state_gas` are added to `block_execution_gas_used` and `block_state_gas_used`, as in [EIP-8037](./eip-8037.md). With the repricing surcharge, `tx_execution_gas` of a failed settlement can be greater than `tx_gas_paid` (see [Underpaid work of failed transactions](#underpaid-work-of-failed-transactions-repricing-surcharge)).

A settlement failure is processed as an exceptional halt of the top-level frame: all state changes of the execution are rolled back, `gas_left` is consumed, the refund counter is set to zero and `state_gas_used` is set to zero. The [EIP-7702](./eip-7702.md) authorizations stay applied, and `committed_state_gas` stays charged. The receipt status is `0`.

A settlement failure is not an out-of-gas condition of any frame. Clients SHOULD report it in traces with its own error, for example `state gas settlement failed`, at every level: on the instruction whose charge exceeds `state_gas_limit`, on each frame that stops, and on the transaction. A failure at the end of the transaction is reported on the top-level frame and the transaction only.

The unused part of `tx.gas` is returned to the sender.

### Repricing surcharge (extension)

This section is a separable extension. It applies the settlement to the execution-gas increases of [EIP-8038](./eip-8038.md), so that deployed contracts see no repricing inside call frames.

A transaction-level counter `surcharge_used` starts at zero. It only increases: a revert or an exceptional halt does not decrease it, because the work was done.

- The surcharge is defined per charge stage, not per instruction. A stage is a group of charges that is paid as a whole:
  - The **pre-access stage** of an instruction has all charges that [EIP-7928](./eip-7928.md) requires before the first state access of the instruction: the base cost, memory expansion, copy cost, the value charge and the access charge of the first account or slot.
  - Each **further account access**, which is the delegation target that a `CALL*` resolves, is its own stage, before that account is accessed.
  - Each **post-access charge**, such as the rest of an `SSTORE` after the slot is read, or the second part of an account-creating `CALL` or `SELFDESTRUCT`, is its own stage.

  A stage takes the total of its charges before [EIP-8038](./eip-8038.md) from `gas_left` in one step. Only if that succeeds, the stage adds the total of its surcharges to `surcharge_used` and runs the check below. A stage that `gas_left` cannot pay fails as a whole and adds no surcharge. A stage that succeeded keeps its surcharge when a later stage of the same instruction fails.

  | Charge | Charge to `gas_left` (warm / cold) | Added to `surcharge_used` (warm / cold) | Stage |
  |---|---|---|---|
  | Account access: the target of `BALANCE`, `EXTCODE*` and `CALL*` | 100 / 2,600 | 0 / 400 | Pre-access |
  | Beneficiary access of `SELFDESTRUCT` | 0 / 2,600 | 0 / 400 | Pre-access |
  | Second read of `EXTCODESIZE` and `EXTCODECOPY` | 0 | 100 | Pre-access |
  | Value transfer of `CALL` and `CALLCODE` | 9,000 | 2,300 | Pre-access |
  | Slot access of `SSTORE` | 0 / 2,100 | 0 / 0 | Pre-access |
  | Access of the delegation target that a `CALL*` resolves | 100 / 2,600 | 0 / 400 | Its own stage |
  | Rest of `SSTORE`, first change of an existing slot | 2,900 | 7,200 / 7,100 | Post-access, after the slot is read and before it is written |

  The surcharge of a stage depends only on information that is known at that stage. Examples:
  - A zero-value `CALL` to a cold account with 3,000 gas and a memory expansion of 603 gas needs 3,203 for its pre-access stage. The stage fails as a whole: the target is not accessed and no surcharge is added, whatever the order in which a client computes the charges.
  - A `CALL` to a cold account that delegates to a cold account adds 400 for each of the two accesses. If `gas_left` cannot pay the second access, the first account is in the block access list and its 400 stays in `surcharge_used`; the delegation target is not accessed and adds nothing.
  - `SELFDESTRUCT` does not resolve a delegation, so it has only its pre-access stage and, if it creates an account, the second part of its charge. A warm beneficiary costs nothing, as under [EIP-2929](./eip-2929.md).
- The state-creating operations of this proposal take their complete charge before [EIP-8037](./eip-8037.md), as specified above, and their stages are part of that charge: with this extension, the first part of the two-part charge of a `CALL` or `SELFDESTRUCT` is the charge before [EIP-8038](./eip-8038.md) (for example 2,600 + 9,000 for a cold `CALL` with value), and the second part is 25,000. Their access and value stages add the surcharge in the table, as for any other instruction. Where [EIP-8038](./eip-8038.md) lowers a charge, for example a cold `SSTORE` that does not change the slot (2,200 before, 2,100 after), the stage keeps its charge before [EIP-8038](./eip-8038.md) and adds no surcharge.
- Intrinsic gas and the refund counter use the values of [EIP-8038](./eip-8038.md) directly, because contracts cannot observe them during execution. The exception is the refund for restoring an originally zero slot to zero, which stays 19,900 as specified in [Execution-gas of state-creating operations](#execution-gas-of-state-creating-operations).
- After each increase of `surcharge_used`, and after each state-gas charge, the check during execution is `state_gas_used + surcharge_used > state_gas_limit`. If it is true, the transaction fails at once with a settlement failure, as in [State-gas during execution](#state-gas-during-execution). A failed check at a stage before an access means that the account or slot is not accessed. A failed check after a slot read means that the slot is in the block access list but is not written. For example, with `tx.gas` 100,000 and intrinsic gas 15,000, cold updates of existing slots stop at the 12th update (surcharge 85,200 > 85,000): its slot is read and enters the block access list, but it is not written, and no later instruction runs. The ceilings of call frames do not include `surcharge_used`.
- The check runs only at a state-gas charge and at an increase of `surcharge_used`. A rollback can raise `state_gas_used`, for example when a reverted child had cleared a slot that its parent created. The rollback itself does not run the check: the next charge or increase checks the new total, and settlement checks the final total.
- Settlement charges `state_gas_used + surcharge_used`, as specified in [Settlement](#settlement). On a settlement failure, the sender can pay less than `tx_execution_gas`, because `tx_gas_paid` is capped at `tx.gas`.
- The transaction-validity check for the execution dimension becomes:

  ```python
  budget = min(TX_MAX_GAS_LIMIT, tx.gas)
  reservation = max(calldata_floor_gas_cost, intrinsic_gas + (budget - intrinsic_gas) * 7 // 2)
  assert reservation <= execution_gas_available
  ```

  The charge of an instruction is raised at most 3.5 times, by the first change of a warm existing slot (2,900 before, 10,100 after). Intrinsic gas already uses the prices of [EIP-8038](./eip-8038.md) and has no surcharge, so only the execution budget is multiplied. This is the most execution-gas a transaction can add to the block. The check reads no state.
- `STATEGAS` returns `state_gas_used + surcharge_used`, the gas that settlement will charge so far.

### System calls

System calls get `30_000_000` `gas_left` and no settlement. Their state-gas is not limited and does not count toward the block. `SYSTEM_MAX_SSTORES_PER_CALL` is removed. The execution-gas of state-creating operations in this proposal applies to system calls too.

### Frame transactions

This proposal does not specify transactions of [EIP-8141](./eip-8141.md), which have separate execution-gas and state-gas limits per frame. Those transactions keep the rules of [EIP-8037](./eip-8037.md) for their frames until an extension of this proposal defines them.

## Rationale

### The cause is the per-transaction execution cap

[EIP-7825](./eip-7825.md) caps a transaction at `TX_MAX_GAS_LIMIT` (16,777,216). With `CPSB = 1530`, a cap that also included state-gas would limit a deployment to about 7.5 kB. [EIP-8037](./eip-8037.md) therefore applies the cap to execution-gas only. Because a transaction has one gas limit, it must decide how to split `tx.gas` between the two dimensions before it knows how much of each the execution will use. The reservoir makes that decision at the start and corrects it during execution, which is the source of the frame-visible effects listed in the motivation.

At the end of the transaction, the split is known. Execution-gas is limited by `gas_left`, which starts at no more than `TX_MAX_GAS_LIMIT - intrinsic_gas`. State-gas is limited by what is left of `tx.gas`. No split has to be guessed, and nothing has to be corrected.

### Frames do not see state-gas

With this proposal, no amount that a contract can observe depends on state-gas:

- `gas_left` only decreases within a frame, and a call returns at most the unused gas of the child, as before [EIP-8037](./eip-8037.md).
- The gas that a frame needs for an operation does not depend on `tx.gas`. A sub-call budget that was sufficient for creating slots and accounts and for `CREATE` before [EIP-8037](./eip-8037.md) is still sufficient for them, whoever sends the transaction.
- A transaction that does not supply enough gas for its state fails as a whole. A contract cannot catch this failure, so it cannot be used to make a contract record a failure of an operation that was given too little gas.

The repricing of [EIP-8038](./eip-8038.md) still changes the execution-gas of operations that do not create state. This proposal does not change that.

### Execution-gas of state creation

[EIP-8038](./eip-8038.md) charges a new slot 10,000 execution-gas plus access, because [EIP-8037](./eip-8037.md) moves the cost of the new state to state-gas. When the state-gas does not come from the frame, a frame could then create a slot for less gas than before (12,100 instead of 22,100 when cold). A contract that expects its failure handler to run out of gas could then record a failure it could not record before.

This proposal charges each new slot, new account and `CREATE` exactly its complete charge before [EIP-8037](./eip-8037.md), for the same warm or cold case. A component-wise floor would not be exact: for example, `WARM_ACCESS + max(STORAGE_WRITE, 20000)` is 20,100 for a warm new slot, 100 more than the 20,000 before, so a budget of exactly 20,000 would fail. With the exact charges:

- A budget that was sufficient for these operations before [EIP-8037](./eip-8037.md) is still sufficient, and a frame that ran out of gas on them before still runs out of gas.
- The state-gas that a frame can create per unit of gas is limited to about 4 to 6 times for slots and accounts.
- A transaction can create about as many slots as before [EIP-8037](./eip-8037.md) under [EIP-7825](./eip-7825.md).

The total cost of a new slot is about 10,000 gas (about 9%) higher than under [EIP-8037](./eip-8037.md).

The code deposit keeps the execution-gas of [EIP-8038](./eip-8038.md), which is much lower than the 200 gas per byte before. A charge of 200 gas per byte would again limit deployments by `TX_MAX_GAS_LIMIT`, which [EIP-8037](./eip-8037.md) intends to remove. Thus a frame can deploy code with less `gas_left` than before. Inside a call frame, the allowance still limits the deployed bytes to what the forwarded gas could buy before. A failure handler that deploys code is not a known pattern.

### Failure at the end of the transaction

[EIP-8037](./eip-8037.md) rejects charging the account creation of `CREATE` after the create frame exits, because a successful deployment could then run out of gas at the frame exit. Settlement does not have this problem: it does not fail a frame, it fails the whole transaction, as an out-of-gas of the top-level frame does. `eth_estimateGas` finds the required `tx.gas` in the same way as for execution-gas.

### Bound on unpaid state during execution

`state_gas_used` is paid only at the end. Without a bound, a transaction could hold much more unpaid new state during execution than it can pay for, for example by deploying large contracts with little execution-gas. The check against `state_gas_limit` limits this to what `tx.gas` could pay for if the execution used no gas, which is the same limit as with the reservoir. The check uses a value that is fixed for the transaction, so it is simple to compute at every charge. The exact check is done at settlement.

Execution stops at once when the check fails. Execution that continued could not change the result, because the transaction fails and `gas_left` is consumed in both cases. But it would access more accounts and slots, and these accesses would enter the [EIP-7928](./eip-7928.md) block access list. Stopping at once makes the block access list of a failed transaction unambiguous.

### `gas_left` includes gas that settlement can need

Under [EIP-8037](./eip-8037.md), a state-gas charge without a reservoir lowers `gas_left` at once. With this proposal, `gas_left` is not lowered, and the gas stays available for execution until settlement. Two effects follow:

- `GAS` returns more than under [EIP-8037](./eip-8037.md) after state creation, and a transaction with `tx.gas <= TX_MAX_GAS_LIMIT` cannot have a small `gas_left` and a state budget at the same time.
- A frame that forwards all its gas forwards gas that settlement can need later. For example, a child `CREATE` that fails consumes 63/64 of a `gas_left` that the account-creation charge did not lower, so it consumes about 63/64 of `STATE_BYTES_PER_NEW_ACCOUNT × CPSB` more gas than under [EIP-8037](./eip-8037.md).

Both effects match the gas semantics before [EIP-8037](./eip-8037.md), where all gas was available for execution. A sender who wants a frame to keep gas for settlement must supply it in `tx.gas`.

### State-gas allowance

Before [EIP-8037](./eip-8037.md), the gas that a caller forwards limited everything that a callee could cost, including state: the cheapest new state byte cost `LEGACY_GAS_PER_STATE_BYTE` (200) gas, as code deposit. Contracts that call untrusted code rely on this. Without an allowance, settlement removes this limit: a callee can deploy a large contract for little execution-gas, and the debt can fail the whole transaction, which no caller can catch.

The allowance restores the limit with the only input that deployed contracts give, the forwarded gas. A frame with `g` gas can create at most `g / LEGACY_GAS_PER_STATE_BYTE` new state bytes, which is what `g` gas could buy before [EIP-8037](./eip-8037.md). Thus:

- The allowance never fails a call whose execution creates no more new state bytes than its gas could buy before [EIP-8037](./eip-8037.md). On the same execution path, a gas budget that was sufficient for state creation stays sufficient. A path that depends on `GAS` can create more state than before, because the code deposit now takes less execution-gas, and can then exceed the allowance (see [Backwards Compatibility](#backwards-compatibility)).
- A callee can create at most about `7.65 × g` of state-gas (`CPSB / 200`). The allowance limits what untrusted code can cost, but it does not pay for it. A sender that executes untrusted code avoids a settlement failure only if `tx.gas` covers its execution-gas, its own state-gas, and `CPSB / LEGACY_GAS_PER_STATE_BYTE` times all the gas it forwards to untrusted code. This amount must also fit `TX_MAX_TOTAL_GAS_LIMIT` and the free state capacity of the block, so it is not only a question of balance. For example, a bundle that forwards 16M gas to user operations needs about 122M of state-gas capacity for the worst case.
- The allowance depends only on the forwarded gas. `tx.gas` does not change it, so the sender cannot use it to make a call fail that would succeed otherwise, beyond what the forwarded gas already allows.
- When a frame exceeds its allowance, only that frame fails. The caller handles it as an out-of-gas of the callee.

The ceiling of a child is never above the ceiling of its parent, so the net state-gas of a frame and all its descendants stays within the frame's allowance. Because the parent does not run while the child runs, only the frame that is charged must be checked. An absolute ceiling gives the same result as a net state-gas and an allowance per frame, also when the net state-gas of a frame is negative, without a subtraction at each check. The rollback of a frame still uses the value of `state_gas_used` at its entry.

The allowance limits deployments from a call frame: a frame with 16.7M gas can deploy about 83 kB of code, as before [EIP-8037](./eip-8037.md). This is sufficient for a contract of the maximum size of [EIP-7954](./eip-7954.md). The top-level frame has no allowance, so a deployment from the transaction itself, or from a factory that the transaction calls directly, is limited only by `tx.gas`.

A lower ratio, for example from the 312 gas per byte of a new slot before [EIP-8037](./eip-8037.md), would expose senders less. But it would fail deployments from call frames that the same gas could complete before [EIP-8037](./eip-8037.md).

### `STATEGAS`

`gasleft()` differences do not include state-gas, so contracts that bill a sub-call for its work, such as an [ERC-4337](./eip-4337.md) `EntryPoint`, cannot bill state-gas. `STATEGAS` lets new contracts measure it: the state-gas of a sub-call is the difference between two `STATEGAS` reads around it. The opcode exposes a value that the transaction already has. It does not change the cost or the result of any other operation.

The difference can be negative, for example when a sub-call clears a slot that an earlier call created in the same transaction. A billing contract must compute it with signed arithmetic, because an unsigned subtraction reverts or wraps. It must also choose how to attribute a negative amount, for example as no charge, or as a credit to the sub-call that removed the state. A deployed contract that bills by `gasleft()` cannot use `STATEGAS`, so its operator must charge for state-gas in another way.

### Repricing surcharge

A repricing that raises execution-gas can make a fixed gas budget of a deployed contract too small. For example, [EIP-8038](./eip-8038.md) raises the first change of a cold existing slot from 5,000 to 12,100, so an [ERC-20](./eip-20.md) transfer to an existing holder costs about 14,200 more. Where a contract records such a failure permanently, the repricing causes a permanent loss. The surcharge keeps the costs inside call frames at their values before [EIP-8038](./eip-8038.md), and the sender still pays the new prices through settlement.

- **Work per transaction.** `gas_left` is still capped at `TX_MAX_GAS_LIMIT - intrinsic_gas`, but in prices before [EIP-8038](./eip-8038.md). The most work that one transaction can do is therefore the same as before [EIP-8038](./eip-8038.md), up to 3.5 times `TX_MAX_GAS_LIMIT` in [EIP-8038](./eip-8038.md) prices for a transaction of only warm storage updates. The extension gives up the tighter limit per transaction that [EIP-8038](./eip-8038.md) would add. It keeps the limit per block: `surcharge_used` counts as execution-gas of the block.
- **No allowance needed.** The surcharge of a charge is at most 2.5 times its value inside the frame. So the surcharge of a call frame is at most 2.5 times the gas it was given, and a sender can make settlement safe by its choice of `tx.gas`.
- **Not undone by a rollback.** The surcharge pays for work that was done, so it stays when a frame reverts or halts, as consumed gas does.
- **Future repricings.** The same rule can apply to later repricings, so that deployed contracts never see a repricing inside a call frame.

### Authorizations are paid before execution

[EIP-7702](./eip-7702.md) authorizations stay applied when execution fails. Their state-gas must therefore be paid even if settlement fails, so it is taken from `tx.gas` before `gas_left` is set.

### What is removed

Compared with [EIP-8037](./eip-8037.md), this proposal removes the reservoir, the four frame-level counters, the last-in, first-out refill order, the merge step, the restore and commit rules, the partial reservoir of system calls, and the rule that the `GAS` opcode excludes the reservoir. It adds one journaled counter, an allowance per frame, two checks at each state-gas charge, one check at the end of the transaction, and the `STATEGAS` opcode.

## Backwards Compatibility

This is a backwards-incompatible change of the gas model that requires a scheduled network upgrade. It is intended to be activated together with [EIP-8037](./eip-8037.md), instead of the reservoir model.

- `GAS` and the forwarding of gas to calls behave as before [EIP-8037](./eip-8037.md). The difference between two `GAS` reads is never negative.
- `gasleft()` differences do not include state-gas. Contracts that use them to charge a user for the work of a sub-call, for example the [ERC-4337](./eip-4337.md) `EntryPoint`, do not charge for state-gas. This is the same as for state-gas taken from the reservoir under [EIP-8037](./eip-8037.md), and similar to fees that rollups charge outside of gas. New contracts can use `STATEGAS`.
- A call frame that creates more state than its forwarded gas could buy before [EIP-8037](./eip-8037.md) fails with an exceptional halt. A contract that deploys code in a loop until `gasleft()` is low, inside a call frame, now runs more iterations, because the code deposit takes less execution-gas, and can exceed its allowance. Before, the same loop stopped earlier and succeeded.
- `STATEGAS` is a new opcode. `0x4c` was an undefined instruction before.
- A transaction can fail at settlement after its execution completed. Wallets must use `eth_estimateGas`, which includes the settlement.
- `GAS` returns more than under [EIP-8037](./eip-8037.md) after state creation, and a frame that forwards all its gas forwards gas that settlement can need (see [`gas_left` includes gas that settlement can need](#gas_left-includes-gas-that-settlement-can-need)).

## Security Considerations

### Cost of untrusted code to the sender

The allowance limits the state-gas that a sub-call can create to `CPSB / LEGACY_GAS_PER_STATE_BYTE` (about 7.65) times the gas forwarded to it. The sender pays for this state-gas. A contract that bills sub-calls by `gasleft()` differences, such as a deployed [ERC-4337](./eip-4337.md) `EntryPoint`, does not bill it. A bundler or relayer that uses such a contract must simulate the transaction and charge for the state-gas in another way, for example through `preVerificationGas`, or accept the cost. New contracts can bill it with `STATEGAS`. Under [EIP-8037](./eip-8037.md) the same applies when the transaction has a reservoir, without a limit per sub-call.

### Untrusted code cannot fail the whole transaction

Without the allowance, a sub-call could create more state-gas than the transaction can pay, for example by deploying a large contract with little execution-gas. The settlement would then fail the whole transaction, and no caller could catch it: one bad user operation could make an [ERC-4337](./eip-4337.md) bundle fail. With the allowance, a sub-call that exceeds its limit fails alone, and its caller continues.

The allowance check comes before the check against `state_gas_limit`, so one charge that exceeds both fails only the frame. Test vector: a transaction with `tx.gas` of 1,000,000 forwards 50,000 gas to untrusted code (allowance 382,500). The code runs `CREATE` with the init code `0x6160005ff3`, which returns 24,576 zero bytes. The execution fits the forwarded gas, and the account-creation charge (183,600) fits the allowance. The code deposit (37,601,280) exceeds both the allowance of the create frame and `state_gas_limit`. Only the `CREATE` fails; the transaction continues.

A sender that funds `tx.gas` as described in [State-gas allowance](#state-gas-allowance) cannot get a settlement failure from untrusted code. A sender that funds less, or cannot fit the worst case into the transaction and block limits, can still get one.

### Wasted execution

A transaction that fails at settlement pays for all of its execution-gas, as a transaction that runs out of gas does. Its new state is not written. Nodes and builders are paid for all work they do.

### Unpaid state during execution

The check against `state_gas_limit` limits the new state that a transaction can create during execution to the state that `tx.gas` could pay for.

### Underpaid work of failed transactions (repricing surcharge)

With the repricing surcharge, a transaction can do work whose surcharge it cannot pay: it uses all of `gas_left` on storage updates, and settlement fails. The sender then pays all of `tx.gas`, which covers the work at the prices before [EIP-8038](./eip-8038.md) but not at the new prices. The block still counts the full work, so the block limit is kept. But such a transaction raises the base fee by more than it pays for, by at most 3.5 times. The work and the price are the same as before [EIP-8038](./eip-8038.md), and the state changes of the transaction are rolled back.

### Block building

A builder learns the gas that a transaction uses only after it executes the transaction, as before this proposal. Settlement does not change this, and every included transaction pays, also when settlement fails. Two things change:

- The validity check before execution must reserve the most that a transaction can use: `tx.gas` in the state dimension, as in [EIP-8037](./eip-8037.md), and, with the repricing surcharge, 3.5 times `min(TX_MAX_GAS_LIMIT, tx.gas)` in the execution dimension. Near the end of a block, a transaction can therefore be rejected although its actual use would fit. The loss is at most one reservation per block and dimension.
- A transaction with a large `tx.gas` for state, such as a large deployment, needs that much free state capacity. It fits only in a block that has not used much state yet.
